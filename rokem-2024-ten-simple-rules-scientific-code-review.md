# Ten simple rules for scientific code review

Rokem A. PLoS Computational Biology, 2024.

## Summary

Ten practical rules on why, when and how to review research code. The article argues that continual review by others is part of rigorous research, works best when reviewers bring both technical and domain knowledge, and gives guidance for reviewing within a team and beyond it.

## Why It Matters

[[kenji-mori]] proposed it as pre-reading for the "how we work" day of the [[group-retreat-2026]], after the [[retreat-2026-pre-survey]] showed that only Tobias felt able to change the pipelines. It shaped the [[code-review-guidelines]] adopted at the retreat, especially reviewing small changes often rather than large ones rarely, and pairing a domain reviewer with a technical one for analysis code. It also informs the stance in [[code-review-in-small-labs]].

## Key Details

- Review should be continuous, part of normal work rather than a gate before publication.
- Reviewers with domain expertise catch different problems from those with software expertise.

## Caveats

General guidance, not evidence from a controlled study. It does not settle how much review a group of our size can afford; that is still [[should-we-require-code-review-for-all-pipeline-changes]] for analysis code outside the pipelines.
